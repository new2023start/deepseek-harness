# 事故复盘 0005：一次「清理残留目录」把整个工作区根目录删掉了

[English](0005-skill-home-consolidation-deletes-workspace-root.md) | 中文

状态：已解决（数据已恢复）

## 执行摘要

一个 agent 会话在把重复的 `.claude` 技能目录合并到唯一的规范技能目录。它写的 PowerShell 辅助脚本里带了中文路径；由于脚本是「UTF-8 无 BOM」保存、再用 `powershell -File` 执行，Windows PowerShell 按 ANSI 代码页解码，脚本实际创建的是一个**乱码同名目录**，而不是预期的那个工作区目录。agent 发现后，又写了一段清理逻辑，**用「列出 `E:/`、取第一个以 `00-` 开头的目录」来认定"残留目录"**。当时唯一符合的就是真实工作区 `E:\00-学习`；清理逻辑把它当成残留树，把条目往乱码路径里 rename，随后 6 秒内该工作区被递归删除——55,064 个文件、13.8 GB。教训是：**删除目标绝不能靠模式推导，只能是刚刚被创建的那个确切规范路径；对不上就必须中止。**

## 概述

合并本身是合理需求：六个技能目录同时存在于 `C:\Users\Administrator\.claude\skills` 和 `C:\Users\Administrator\.openclaw\workspace\skills`。计划是把 `.claude` 那份移入工作区内带日期的回收目录，再在原位置留一个指向规范副本的 junction。

辅助脚本里嵌了中文路径（`E:\00-学习\_trash\...`）。脚本以 UTF-8 无 BOM 写盘、由 `powershell -File` 执行，Windows PowerShell 用 ANSI 代码页解码，于是创建了一个**按乱码渲染**的同名目录；而脚本打印的每条路径回显时又都是正确的，所以在会话记录里看不出异常。

agent 察觉到目标回收目录仍为空，尝试把六个目录按精确路径移回，全部报 `ENOENT`。随后它改写了搬迁逻辑，改为动态发现乱码根目录：

```js
const roots = fs.readdirSync('E:/', { withFileTypes: true })
  .filter((e) => e.isDirectory() && e.name.startsWith('00-'))
  .map((e) => e.name)
```

此时乱码目录已被清掉或本就无法匹配该前缀，`roots` 里只剩下真实工作区。脚本打印 `stray root = 00-学习`，把真实工作区的条目 rename 进乱码路径，紧接着的删除动作把工作区本身删掉了。

## 影响

- 工作区 55,064 个文件（13.8 GB）被删除：笔记、项目源码、文档、agent 记忆。
- 删除未进回收站，该卷也没有卷影副本，常规撤销不可用。
- 删除时仍被占用的条目先进 `$Extend\$Deleted` 再删除，这部分记录已被系统回收，无法找回。
`winfr`（微软 Windows File Recovery）常规模式恢复了 55,065 条目录项，原始路径、文件名、大小都在——但这不等于恢复了数据。该卷是开启 TRIM 的 NVMe SSD（`fsutil behavior query DisableDeleteNotify` 返回 0），主控早已把释放的 LBA 清零。事后抽样：400 个文件中 302 个开头全是 0；30 个 PDF/DOCX/xlsx 中 0 个签名有效。只有常驻 MFT 记录的小文件幸存：约 700 字节以下的 12,836 个文件里有 12,004 个内容完好（合计 3.0 MB），其余 42,229 条只剩文件名和大小，数据块已经不存在。

## 时间线

- agent 编写合并辅助脚本，并从 `run_code` 启动；脚本里唯一的非 ASCII 路径就是工作区回收目录。
- 脚本创建了工作区的乱码同名目录，把六个技能目录移进去，并在原位置建立 junction。
- agent 发现预期回收目录仍为空，探查 `E:` 根目录，定位到乱码树。
- 按精确路径搬迁的脚本失败（`ENOENT`），改写为用 `readdirSync('E:/')` 前缀过滤来发现根目录。
- 改写后的脚本报告 `stray root = 00-学习`，并从真实工作区向乱码路径发起 rename。
- USN 日志显示，工作区目录在 11:32:29 至 11:32:35 之间被删除，顶层目录最后删除。
- 11:53 开始恢复；`winfr` 常规模式按原始路径恢复 55,065 个文件，空闲空间雕刻 0 命中，证明剩余簇已被回收。

## 根因

**非 ASCII 路径无法在「无 BOM 脚本」里存活。** `powershell -File` 会用 ANSI 代码页解码无 BOM 脚本，把 `E:\00-学习` 悄悄改成另一个路径；脚本回显时又被正确解码，所以会话记录里看不出来。任何**先按该路径写入、之后又按该路径删除**的工具，都必须验证「我创建的那个路径」和「我现在要操作的那个路径」是同一个值。

**删除目标是由模式推导出来的。** 清理需要的是「我刚才误创建的那个目录」，这是完全可以精确知道的：就是脚本打印过的那个路径。把它换成「`E:/` 里第一个以 `00-` 开头的目录」之后，工作区就成了候选。当真正的残留条目消失时，模式静默地选中了真实工作区。这一步既没有「目标必须等于刚才创建的对象」这一不变式，也没有「目标不能是工作区根目录」的检查。

**两个失误叠加。** 乱码制造了一个本不该存在的树；前缀发现随后选中了唯一绝不能删的目录。任一防护单独存在，损失都不会发生。

## 已加的防护

- 删除路径禁止用模式推导。把「刚创建的确切路径」作为值传入清理逻辑，不存在就中止。
- 递归删除前断言：目标不是工作区根目录、不是当前工作目录的祖先、不是通过 junction 抵达的。
- 把「我刚创建的路径」和「我接下来要删的路径」当作同一个值传递，不允许模型事后重新计算。
- 非 ASCII 路径必须跨 shell 边界时，脚本写成 UTF-8 带 BOM（或以参数传入），创建后立即验证存在性。
- agent 做目录整合时采用 复制 → 校验 → 最后删除，校验失败时源保持完整。

## 教训

- 路径在会话里显示正确，不等于字节正确。
- 「按前缀找到再删掉」即使谓词看起来无歧义也是危险惯用法；问题不在谓词宽窄，而在「推导」本身。
- 为修复错误而临时写的清理脚本，是 agent 产出的最高风险代码：无人值守、直指用户数据、通常零测试。
- 恢复成本远高于预防成本：这次事故花掉约一小时取证加两轮全卷扫描，最终没能救回任何一个大于 1 KB 的文档。
- 在 SSD 上，删除即毁灭。MFT 恢复能拿回文件名与大小，看起来像是成功，直到你打开内容；「文件很新，应该能恢复」在 TRIM 下是错的。
